# Pi voice architecture (`pi-voice/` + headless Voice.app)

Moved verbatim from CLAUDE.md; CLAUDE.md keeps the map and the rules.

A Pi 1.x extension (tested on 1.1.0, the pinned dev types), not a standalone app. `/voice` spawns one headless `Voice.app` child (`--headless`, `VOICE_THINKER=luna`) that talks NDJSON over stdio (`HeadlessBridge.swift`):
- `contracts/pi-voice.json` is the source of truth for every cross-language seam (stdio messages, job statuses, `VOICE_HISTORY`, the two tools, `[STATUS]`/`[FINAL]` tags); change it and each side's conformance test together.
- Wire contract out: `ready`, `error` (`message`), `speech_started`, `heard` (`text`, `item_id`), `spoken_delta` and `spoken` (`text`, `item_id`), `work` (`id`, `brief`), `stop_work`.
- An audio start failure (no IO cycle within 2s, e.g. lid closed; mic denied; engine failed) sends `error` with a readable message, then exits 3. Never call `AVAudioPlayerNode.play()` before the engine has rendered once: it raises an uncatchable `player did not see an IO cycle` exception. `-voice.simulateNoAudioIO YES` (launch argument) exercises this path.
- Wire contract in: `user` (`text`; interrupts any in-flight response first), `mute` (`muted`), `interrupt`, `result` (`id`, `speak`, `full`; Swift falls back to `speak` without `full`), `job_update` (`id`, `status`, `note?`; status is `queued`/`working`/`done`/`stopped`/`superseded`/`dropped`/`failed`, and an empty id or status is ignored), `quit`. Unknown types are ignored; stdin EOF quits. The TypeScript side of this contract is typed in `child.ts`.

Agent's headless tools are defined in `macos/Voice/Sources/Session/VoiceTools.swift` (`HeadlessTools`); `LiveVoiceBackend.swift` is split by role into `LiveVoiceBackend+Realtime.swift` (WS events), `+Tools.swift` (session.update, tool calls) and `+PiJobs.swift` (results, job updates, journal); `PiJobTracker.swift` caches results (last 10; tests can page a cached answer at 4000 characters). `index.ts` is the extension entry point (`pi.extensions` in `package.json`) and hooks `message_start` / `agent_settled`.



**Parallel workers (default).** The durable host is the job runner unless `VOICE_WORKERS` is one of `single`/`steer`/`pi`/`off`, which falls back to the single Pi session. Because it is the default, a host that cannot start (or exits) raises `workerError`: the extension warns once, drops the `worker` marker so later jobs use `sendWork`, and the call continues — a voice call without a job runner would be far worse. `pi-voice/src/worker.ts` starts `pi-voice/src/worker/host.mjs` once per call; the host opens one `pi-durable` Harness and gives each job its own conversation, model, thinking level and tool loop. The wire is the `worker` section of `contracts/pi-voice.json` (NDJSON: `spawn`/`stop`/`status`/`list` in, `ready`/`progress`/`job`/`result`/`status`/`list`/`error` out). A second brief is a second job, so `openJob` does not mark the first `superseded` and the handoff ack returns `started_alongside` (`PiJobTracker.handoffAck(_:steering:parallel:)`) instead of claiming a replacement. `check_thinking` is answered by the host's own job record (`workerAsk` → `workerStatus`), not the local mirror. The default path is untouched: without the variable, voice behaviour is identical to before. Workers never prompt, because a background job has nobody to ask — Codex's workers follow the same rule and carry an inherited `sandboxPolicy` instead. Pi has no sandbox setting to inherit (its settings carry no approval or sandbox keys), so the policy is defined in `pi-voice/src/worker/config.mjs`: `VOICE_WORKER_SANDBOX` is `workspace-write` (default), `read-only`, or `unrestricted`, with extra writable roots from `VOICE_WORKER_WRITE_ROOTS`. `write` and `edit` refuse a path outside the roots (resolved with `realpath`, so `..` and symlinks cannot escape) with a refusal the voice model is told to say plainly and not retry; `bash` runs under `/usr/bin/sandbox-exec` with an SBPL profile denying `file-write*` outside the roots, the same mechanism the Python research tool uses. The host gives each job Pi's own text tool set — `bash`, `read`, `write`, `edit`, `grep`, `ls`, `find` — plus `skill` (lists the installed skills, or loads one's `SKILL.md` from `~/.pi/agent/skills`, `~/.agents/skills`, or the project's own skills folder) and `screenshot` (captures the frontmost layer-0 window with `screencapture` and returns a PNG content block, falling back to the whole screen). That is what makes a worker interchangeable with the session for the requests a voice user actually makes; MCP is the one remaining difference and it is unconfigured on this machine. The host runs on the model the user's Pi session is configured with, resolved the way Codex resolves a worker's config: `~/.pi/agent/settings.json` gives the default provider and model, the catalog under `~/.pi/agent` gives that provider's `baseUrl`, `api` and full model records (`pi-voice/src/worker/config.mjs`; `api` and `baseUrl` are stamped onto each model because the catalog keeps them at the provider level). `VOICE_WORKER_PROVIDER`/`VOICE_WORKER_MODEL` pin an explicit pair, and OpenRouter is used only when no Pi config is readable. Each job also gets the project's `AGENTS.md` and `CLAUDE.md` as a `project_instructions` prompt section, so a worker follows the same rules as the session it serves. Credentials come from `~/.config/chatbot/env`; a missing key exits the host with a readable error instead of settling every job `unanswered`. Verify with `node scripts/verify-durable-workers.mjs --jobs 4`. **Crash resume.** Job state is JSONL under `~/.config/pi-voice/workers/run-<iso>-<pid>/`, and one job-record file there maps each voice job id to its conversation — the conversations alone cannot express that mapping, and the voice model addresses jobs by id. On start `resumeTarget()` reopens the newest run with unfinished jobs (`VOICE_WORKER_RESUME=<dir>` names one, `none` starts fresh), `harness.resume()` lets `pi-durable` continue the run, and `resumeUnfinished()` re-registers each job under its voice id and emits `job: working — resumed after a restart (attempt N)`. `settle()` is shared with a fresh spawn, so a recovered job reports exactly like a new one. Bounded like Codex: at most `MAX_CONCURRENT_RESUMES` (2) at once, and past `MAX_RESUMES` (2) the job is reported failed rather than retried forever; a run whose submission is no longer pending is reported failed too, never left silently absent.

Agent's tools under `--headless` are `spawn_thinking`, `check_thinking`, and `stop_thinking`. Casual chat stays with Agent. Real work (files, shell, research, PDFs, code, the screen, computer use) calls `spawn_thinking`, emitting a `work` event (`work` is dropped while muted, reported back as a `dropped` update so the mirror never shows a phantom job). A second dispatch while one runs steers Pi and marks the first id `superseded` on the wire rather than losing it silently; the latest brief wins. Voice.app's tool result says so: a first dispatch returns `status: started`, and a dispatch while a job is active returns `status: steering` with "This was sent to steer the current Pi task. Pi is redirected to this brief and the earlier task is replaced." so Agent says it redirected Pi instead of calling the new task queued. The brief is sent to Pi as a normal message when Pi is idle, and as a steer when busy. The message carries a trailing `[Pi voice job id: …]` marker; `message_start` binds that exact id, and `agent_settled` retrieves only assistant text following that message and before another user message. During a voice job, the extension injects a work section into Pi's system prompt and applies the job's thinking effort, restoring the previous level when the job ends. The effort is per handoff (`spawn_thinking`'s optional `effort`, `off`/`minimal`/`low`/`medium`/`high`, default `off`), carried on the `work` line and stored on the job, which is as close to Codex's `backend_thinking_effort` as this seam allows: Codex puts the level on each provider request, while pi exposes only a session-wide `setThinkingLevel`, so the extension stashes the level once, sets the job's level for the turn it starts, and puts the old one back. `restoreThinking` refuses to overwrite a level the user changed mid-job (it compares the current level against the one the job set). When Pi finishes, the extension sends a short leading excerpt (`RESULT_MAX`, 1500 graphemes) and the complete answer over the `result` wire message. Voice.app gives Agent the excerpt as a `[FINAL]` item, caches the complete answer, and the shared log stores that answer (up to 16,000 characters) with the brief. The visible Pi message is only the brief and the job-id marker (marker last). Pi's model gets each job the way Codex's backend agent gets a realtime handoff (`pi-voice/src/delegation.ts`): `<realtime_delegation>` with `<input>` (the brief) and `<transcript_delta>` (`user:`/`assistant:` lines of what was heard and what Agent said aloud since the previous handoff, ending with the brief as a `user:` line unless the user said exactly that). Typed composer text, tool calls, `[STATUS]`, `[FINAL]`, and job updates are not transcript. The delta is dropped oldest-first past 8 KiB and starts empty after each handoff and at `/voice` start; each field is XML-escaped and capped at 4 KiB (input keeps its start, transcript its end, `…` marks a cut). The extension stores the delegation as a hidden `pi-voice-delegation` session entry (no renderer, not model context) and the `context` hook swaps it in for every voice-job message on each model request, so earlier handoffs stay visible on later turns and after a Pi restart. It is not drawn in Pi's chat or the "Steering:" line. Pi's steer does not abort a running tool; it is delivered after the current tool batch. A `spawn_thinking` whose brief differs from the running job's only in case, punctuation, order, or filler words within 30s (`PiJobTracker.activeRepeat`) answers `already_working` and sends nothing, so Pi's work in progress survives a repeat. Progress is pushed as silent `[STATUS]` context with no follow-up, so Agent does not speak it. Two paths feed it: a structured `progress` wire message on every tool transition (`tool`, `phase`, a 60-char argument summary, and the set of tools still running, so the status line can say "Editing files + 2 more" the way Codex renders its items), and a 3 s loop that is only a floor for a long silent step. Both share `piProgressGeneration` so one note is never injected twice, and both wait for a quiet window (`canInjectContext`) so they cannot cut a sentence. `check_thinking` is the read-only coordination verb Codex's voice agent gets from `read_thread`/`wait_threads`: it sends a `status` line to the extension, which answers with a `snapshot` payload built from Pi's own session (`snapshotFor` in `pi-voice/src/work.ts`: phase, elapsed, doing, running tools, and the head of Pi's answer so far, or the last answer when no job is live). It never binds, steers, or settles the job. Voice.app answers from its local mirror (`PiJobTracker.snapshotPayload`) if the extension does not reply within 2.5 s, so the model is never left waiting on a `function_call_output` that will not arrive. The handoff and `stop_thinking` stay fire-and-forget. There is no `pi_status` or `pi_results` tool. The `$TMPDIR/pi-voice.jobs.jsonl` journal records metadata, not the full answer. The extension mirrors job phases back as `job_update`: queued and working, tool start, partial output, completion or failure, and the beginning of Pi's written answer. If the user cancels, Agent calls `stop_thinking`, which emits `stop_work` and aborts only the voice job's own turn (idle, unbound, or user-typed turns are marked stopped without killing anything else); a `stop_thinking` with nothing running answers `idle` and forwards nothing. `/voice stop` ends the voice call; it does not merely cancel the current job.

Typing in Pi's composer input while voice is on routes directly to Luna as user text. Running `/voice stop` (or a second `/voice`) sends `quit`; Voice stops the launcher process it started, and the backend exits. Logs go to `/tmp/voice-service-startup.log`, `/tmp/chatbot-server.log`, and the extension's stderr log in `$TMPDIR` (`pi-voice.<pid>.stderr.log`).

Voice and Pi share one durable log, `~/.config/pi-voice/history-<id>.sqlite`, keyed by conversation id. `session.json` only remembers which id a working directory opens; `/voice resume` lists every log by id, so a different folder does not hide an earlier thread. Voice turns, the handoff brief, and the full Pi result are appended there. Progress chatter is stored and left out of what the models see.

When `/voice` starts, the extension builds one user-role startup pack from the newest rows that fit `VOICE_REPLAY_KB` (default 16KB, at most 80 turns): a warning that the background may be incomplete or stale, then `Latest` (the last user turn and what followed) and `Previous` (older rows in the window). Each line is dated in RFC3339. Voice.app injects that pack with `conversation.item.create` and does not request a reply, so it is not spoken. Pi does not get this pack; it gets the per-handoff transcript delta (see above). `[Pi handoff]` rows are Agent's briefs and are labelled `Agent`; only `[Pi result …]` rows are labelled `Pi`. The sqlite file is the shared thread. `/voice stop`, and a child failure, write any uncommitted user transcript and partial reply into the log, framed as leftover history rather than a new request. While the log is still empty, the first start imports the last 20 final voice turns from Pi's branch once. `/voice new` starts a fresh id. Override the pack budget with `VOICE_REPLAY_KB`, the config dir with `PI_VOICE_CONFIG`.

In interactive mode, `/voice` stays in Pi's ordinary terminal transcript. Luna's spoken deltas update one visible custom entry in place; a hidden final entry saves the completed text for replay. Pi shows its own native tool calls and answers. The Pi renderer (reviewed bundles: 0.87.1 and 1.1.0, listed in `REVIEWED`) is repaired by `scripts/patch-pi-native-fold.mjs` so voice tool calls and answers start folded and open on click, and the folded answer shows writing/ready state. The script checks the bundle hash, keeps a restore backup, does nothing on an already-patched bundle, and refuses an unreviewed version (`pi-voice/src/patch-fold.test.ts`).

Architecture & purity: `step()` / `handleCommand()` in `voice.ts` (dispatching into `voice-lifecycle.ts`, `voice-transcript.ts`, `voice-job.ts`) and `work.ts` are pure reducers returning `{state, effects}`; the `Voice` class applies effects to the Pi API; `child.ts` owns the child process and the lease file (`$TMPDIR/pi-voice.lease.json` or `tmpdir()`), which blocks a second Pi window from running voice concurrently and reaps orphaned `--headless` Voice processes. Keep new logic in the reducer so it stays testable.
